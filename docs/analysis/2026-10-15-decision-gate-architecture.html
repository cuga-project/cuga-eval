CUGA decision gate: architecture

Superseded by v2: 2026-10-20-policy-gate-architecture-v2.html (all lifecycle hooks, intake ahead of time or on arrival). This page keeps the worked examples.

A strong model turns the policy into checked rules once, in a pluggable policy language. At runtime, CUGA fires a hook at each step; the decision gate and other plugins, such as AgMentor's guardian, check the step: compiled rules first, then a semantic verifier (Boaz) for what no rule covers. After each run, a retrospective checker scores the whole run. Dashed boxes are plugins.

Hooks CUGA exposes

HookFires whenWhat the decision gate does
on_user_messagea user message arrivesrecords facts from the user, e.g. "the user confirmed", the cancel reason
after_plan (optional)the agent writes a plan or a reasoning stepchecks the plan against order rules; AgMentor's guardian also checks reasoning steps
before_tool_callthe agent proposes a tool callchecks the rules for that action; can block the call
after_tool_calla tool returns a resultstores read results as facts for later rules
before_replythe agent's reply is readychecks reply rules, e.g. no claim of an action that did not run; the semantic verifier checks that the reply is grounded
on_task_endthe task ends: final answer, transfer or step limitchecks rules that must happen before the end; reminds the agent once, then reports what is still open; the semantic verifier rejects a final answer given too early

Every hook also writes an event (activity, time, agent, attributes) to the event log. If several handlers return a verdict for one event, the most severe wins: TRANSFER, then DENY, then ASK USER, then ALLOW.

CodeAct (CUGA) vs ReAct and function calling

In CUGA the model writes a Python block that can call many tools, in loops and branches. The gate does not judge the block as text. It wraps each tool function in the block's namespace, where CUGA already counts tool calls (counted_tool_call in code_executor.py). The block awaits each call, so the gate checks every guarded call when it happens, with the real argument values.

The CodeAct problem: a block can stop half-way

Example: a block calls update_reservation_flights, then send_certificate. The gate denies the certificate. The flight change has already happened, and the code the model wrote after the denied call (prints, the summary) never runs. The model must read the denial and write a new block.

OptionHowProCon
1. Check each call (planned)wrapper on each tool functionexact runtime arguments; works with loops and branchesa block can stop half-way
2. Pre-scan the block (add to 1)at after_plan, read the code (Python AST) and list the write tools it may callfetch facts and ask Jev before the first write; can enforce "at most one write per block"cannot decide alone: arguments and branches are known only at runtime
3. Dry run, then commitrun the block with writes recorded but not executed, check them all, then run again for realall-or-nothing blocksreads run twice; code that depends on a write's result breaks; slower

Recommendation: option 1 with the option 2 pre-scan. The "one write per block" rule fits PR #800's plan-then-step rule (each block does only the next step). Then a denial never cuts a block between two writes. Order rules (Declare) work the same in all styles, because every call is one event.

Policy levels decide what a broken rule does

LevelExampleWhen it is broken
Hard constraint"Basic economy flights cannot be modified"the gate blocks the call (DENY, ASK USER or TRANSFER)
Guideline"Look at the cart before checkout"a hint or playbook text to the agent; never blocks
Best practice"Search every result page before choosing"reported in the retrospective check only

Each rule carries a level; the verdict handler reads it. The three levels come from the AgMentor deck (slide 8).

Rules that keep it safe

  • The rules are built only from the policy, tool schemas and approved process sources (BPMN, past logs), never from test answers.
  • Every new policy version passes the build verifiers and a human review.
  • The system never changes its own rules at runtime. Short-term "adaptation" is only feedback to the agent (a verdict message); rules change only in a new reviewed version.
  • If a verifier fails or times out, the gate records it and lets the call through.

Worked example: a cancellation the gate denies

The rules for cancel_reservation, in readable form (the built-in policy language stores the same rules as JSON):

action cancel_reservation                           hook: before_tool_call
  rule cancel.not_flown   require not any_segment_flown        else TRANSFER
  rule cancel.reason      require known(cancel_reason)         else ASK USER
  rule cancel.confirmed   require user_confirmed               else ASK USER
  rule cancel.eligible    require any(booked_within_24h,
                                      airline_cancelled,
                                      cabin == "business",
                                      insurance == "yes" and reason_covered)
                                                               else DENY

fact any_segment_flown  code  get_flight_status of any segment in {flying, landed}
fact booked_within_24h  code  now − reservation.created_at < 24 h
fact airline_cancelled  code  get_flight_status of any segment == cancelled
fact cancel_reason      Jev   choice [change of plan, airline cancelled flight, other]
fact reason_covered     Jev   noul "Is the user's reason for cancelling health or weather?"
fact user_confirmed     Jev   noul "Did the user explicitly say yes to cancelling this reservation?"

The user says: "Please cancel reservation ABC123, my plans changed. Yes, go ahead."

#StepResult
1The agent calls cancel_reservation("ABC123"); before_tool_call firesthe gate finds 4 rules
2Code facts, from reads the agent already madebooked 3 days ago · economy · insurance yes · all segments available
3One batched Jev request with 3 questions (about 1 s, about $0.0002)reason = change of plan · covered = no · confirmed = yes
4Rulesnot_flown ✓ · reason ✓ · confirmed ✓ · eligible ✗ (no branch is true)
5VerdictDENY cancel.eligible, returned to the agent with its message
6tau2never receives the call; the database does not change

The agent then tells the user the reservation cannot be cancelled. With an insured user who said "I am sick", reason_covered is yes, cancel.eligible passes and the verdict is ALLOW.

Reservation ABC123 and the Jev answers are illustrative. Policy rules, tool names and status values are from tau2-bench at commit 5ebebbe (data/tau2/domains/airline/policy.md, src/tau2/domains/airline/tools.py, data_model.py).

Order rules need a stateful language API

A Declare rule describes the whole run, but the gate decides one step at a time. The policy language therefore keeps a state per rule and is called at each hook:

class PolicyLanguage(Protocol):
    def compile(self, policy_md, tools) -> Rules
    def check(self, rules) -> list[Issue]          # build verifier
    def monitor(self, rules) -> Monitor

class Monitor(Protocol):
    def preview(self, event) -> dict[str, State]    # before_tool_call: "would this event break a rule?"
    def step(self, event) -> dict[str, State]       # after the event happened
    def finish(self) -> dict[str, State]            # on_task_end: rules still open
# State: satisfied | violated | temporarily satisfied | temporarily violated

The built-in JSON graph fits the same API; its monitor has no memory.

Must happen eventuallyExistence, Responseon_task_end, then the retrospective checkreminds the agent once, then reports it

Example: Boaz's semantic verifier in the gate

Boaz's internship work (CUGA on τ3 Banking/Knowledge) adds an online verifier that checks each proposed step against the trajectory and either accepts it or rejects it with a reason, so the agent can try again. It covers what compiled rules cannot: claims that are not grounded, contradictions with earlier messages or tool results, made-up arguments, and final answers given too early. In the gate it is one runtime verifier, and its statement graph is one fact source.

Two layers in the gate

  1. Compiled rules decide first (code facts and Jev). Most tau2 airline rules end here: fast, cheap, and the reason is the rule itself.
  2. The semantic verifier runs only when no compiled rule decides, or for checks no rule can express: policies retrieved at runtime from a knowledge base, grounding of replies, contradictions with history.
    • The context graph gives it a small set of atomic statements related to the candidate, instead of the whole trajectory (mostly under 20k tokens, against up to 100k+).
    • It returns accept, or reject with a reason; a reject becomes DENY with that reason as the message.

What his results mean for the design

  • With the graph, the verifier beats a full-context LLM judge in pass-only mode for all 5 models tested: average balanced accuracy 66.3% → 74.2%. In reject-only mode it makes fewer false rejections.
  • With gpt-oss-120b as the verifier, balanced accuracy is 64–68%. A model-only verifier on a small model is not reliable enough alone, which supports deciding with code first and sending only semantic checks to the model.
  • When it rejects correctly, it names the right reason in 90–100% of cases (gpt-oss-120b in reject-only mode: 64%), so its reasons work as DENY messages.

Source: Boaz, "Boaz IBM Internship", October 2026, sections 1–4. Results are on his 422-case τ3 Banking/Knowledge set with golden retrieval.

Hybrid gate: one architecture for all selected benchmarks

In τ2 and EnterpriseOps-Gym the policy is known before the run; in τ³ (knowledge-base results), HANDBOOK.md (a new handbook per task) and AutomationBench-AA (rules in task data) it arrives at runtime. The hybrid gate runs the same compiler at both times, enforces in code, falls back to the semantic verifier when no rule decides, and adds two pieces the other methods lack: authority ranking and required-step checks.

Statement store: a thin graph, not a knowledge graph

Five edge types cover the failures seen so far: applies-to (rule → tool), depends-on (preconditions, always followed), defines, exception-of, supersedes (versions). Stored as JSON, no graph database. Order and time come from the event log, entity facts from the environment's tools.

Detailed design

Decision rules

  1. Earliest decisive layer wins: code, then Jev, then the verifier. Each layer runs only for what is still unknown.
  2. Several rules fire: the most severe effect wins (TRANSFER, then DENY, then ASK USER, then ALLOW).
  3. Level sets what a failed rule does: constraint blocks, guideline sends a hint, best practice is only recorded.
  4. Unknown after all layers: a constraint asks the user (or blocks if no user exists); a guideline lets the step through.
  5. Gate error or timeout: the step goes through and the error is recorded, as in the base design.
  6. Same rule denied 3 times: the agent is told to stop trying that action.

Authority and obligations

  • Labels: every message and value carries its source: policy, user, environment content. A request found in an email or ticket can start work but cannot satisfy a rule that needs approval; approval facts must come from the named source, checked with a tool (e.g. the sender and the approver list).
  • Checklist: obligation rules become a short list shown to the agent before its first action and re-stated before each write (ARQ-style). The monitor marks items done from events; on_task_end sends one reminder for open items.
