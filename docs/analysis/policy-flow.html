1 · Graph methodology

The graph is built in 9 steps; code does most of them, a model fills rule slots, a person reviews

Today the ITSM graph was built by hand and the Oak graph by fixed templates. This is the pipeline that replaces both. Each step says who does it.

StepWhat it doesWhy
1 SplitSections by numbering, tables, preamble included. Page and character span kept only as the citationThe skipped preamble (line 7, "no assumed data") caused the first live ITSM failure
2 ClassifyEach statement → rule, guidance, definition, or out of scope with a reasonA coverage report shows every statement that has no check
3 Link§ references, defined terms, global scope (general sections apply to every write tool), field names in value lists ↔ tool arguments. A model proposes implicit links; a person confirms themClauses far apart in the document must reach the same check (next section)
4 Rule typeFill one of about 12 templates: role permission, threshold, transition, required field, allowed value, required step or order, count / no duplicate, content exclusion, format, duty with deadline, approval, derived valueSlot filling is the only model step in the build; it is checkable
5 CheckerThe cheapest checker that can decide the rule type (table below)Most rules need no model at run time
6 CompileCedar for permissions, Python checks for the rest, typed questions for the decision model. Exceptions and overrides become conditionsOne lookup at run time returns the whole effective rule
7 IndexTrigger keys: tool:, arg:, state:, hook:, entity:Exact dict lookups; no graph search on the hot path
8 VerifyQuotes are verbatim, Cedar validates against the schema, generated allow/deny tests pass, two builds agree. Low-confidence rules go to a personCatches a cut quote (the g_ground problem) and slot errors
9 PublishVersion = policy hash; cache per section. A new variant rebuilds only changed sectionsEnterpriseOps-Gym ITSM has 9 edited versions of one policy

1 · Graph methodology

Links let a clause four sections later change the rule the agent is about to break

Example from our AP policy (AP-SOP-04): §4.2 step 3 says "Run the three-way match (§4.3)". §8.1 says an emergency payment "may skip the matching step (§4.2 step 3)". §4.2 never points to §8.1.

Without linksWith links (built offline)
Chunk search finds §4.2, sees "§4.3" without its text, and misses §8.1 because nothing in §4.2 leads thereEdges are stored both ways, so §4.2 has an incoming exception_of from §8.1. The compiled rule carries the exception and its condition
A small model reads the whole document and skips a far clause (our ITSM urgency failure)The brief shows the rule plus one line per linked clause, with section numbers; policy_get("§8.1") gives the full text
rule match_before_approval            (§4.2 step 3, page 1)
  require: three-way match passed, tolerance from §4.3
  unless emergency payment (§2, §8.1): CFO approval; match within 5 business days (Appendix B)
  unless category in utilities, taxes, government fees (§8.2): AP Manager approval up to $25,000
Our three examples: the AP policy has about 28 explicit § references; the EnterpriseOps-Gym ITSM policy has none, but has global rules at the top and value lists at the bottom that apply to steps in the middle (found by global scope and field-name matching); the Oak document has no cross-references.
2 · Policy intake

Six intake cases: the earlier a policy is known, the more of it is compiled and reviewed

Offline means before the run, with time for the full pipeline and a review. Online means during the run: the rules are added only for this thread, and the work must finish before the agent's next write.

CaseExampleModePathTrust

3 · Policy adherence layer

The adherence layer acts at 9 hooks; only the tool and plan hooks can stop an action

CUGA exposes the hooks through the SDK (CugaAgent(hooks=[...])). The layer looks up rules by trigger key and runs the checkers in cost order. Every verdict records its rule, source line and checker.

HookWhat the layer doesPossible effects
session_startLoad the graph version (policy hash); reset per-thread stateinfo
on_user_messageIntent guards (decision model); rules stated in the request → overlayfixed answer without running the agent; info
before_llm_callPolicy brief: rules for tools in play, open duties, one line per linked far clauseremind
after_llm_callObserve the model outputinfo
after_planPre-scan the CodeAct block: at most one write per block; prefetch factsdeny (block not run, model gets the reason)
before_tool_callRules for this tool, arguments and state: Cedar → code → monitor → decision model → verifier → LLM → humanallow; deny + remedy; modify; ask a person

before_replyOpen duties; reply rules (required notes, no data leak)send the agent back (at most 2 times); rewrite the answer
on_task_endVerdict records, coverage, shadow-mode reportinfo

What we report per task

  • Pass or fail, and verifiers passed (EnterpriseOps-Gym); strict pass and AA-style score (AutomationBench)
  • Gate actions: denies, false denies (a blocked write the grader needed), modifies, follow-ups

Fairness rules

  • 5 tasks per benchmark is a pilot: it shows whether the path works, not a score

6 · Shadow replay

Shadow replay: on the same calls, the layer stopped 0 of the 10 writes that broke a guardrail

The layer's decisions on arm A's own calls, so the agent's path cannot change. For each task: rebuild the world, re-run arm A's logged calls in order, ask the layer before each write, then run the write anyway. A write is violating when it makes a guardrail (negative assertion) newly fail. The replay reproduces arm A exactly: the same 10 broken guardrails in the same 5 tasks.
