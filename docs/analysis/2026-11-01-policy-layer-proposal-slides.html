Proposal: one system that combines the families. Code where the rule is exact, a model where meaning is needed, a step graph for procedures, and intake both before and during the run.

2 · The system

One policy model, filled before or during the run, enforced at CUGA's hooks

  • CUGA does not import the layer; it plugs in only through the hooks API.
  • Nothing is specific to a benchmark: the same code reads any new document or record.

4 · The policy model

A documented model: every rule points back to a sentence, and precedence is explicit

ObjectHolds
PolicySet → Documenttrust, effective date, authority rank
Section → Statementup to 2 of 19 types, modality, verbatim quote
Rule · Procedure/Step · Definitionwhat code, Cedar, the monitor or the verifier checks
Link (7 kinds)refers_to, defines, exception_of, supersedes, depends_on, next, source_of_truth
Fact · Verdictrecords from tool output; allow, deny + remedy, remind

Precedence when two statements disagree:

  1. trusted beats untrusted
  2. explicit supersedes
  3. newer effective date
  4. higher authority
  5. otherwise both only remind; neither blocks

Types come from the benchmark scan: filters 74, format 54, overrides 52, prohibitions 47 of 304 AutomationBench statements; ITSM mostly value lists, transitions, required fields.

model.py and MODEL.md in the package. Type counts: docs/analysis/2026-11-01-policy-xref-and-types.md (hand labels, approximate).

7 · Runtime adherence

Checks run at the hooks in cost order; a check that blocks correct work is turned into a reminder

HookWhat the layer doesEffect
before_llm_callbrief: rules for the tools in play, next procedure stepremind
after_tool_callfacts; online intake; procedure progressinfo
before_tool_callcode → Cedar → monitor → verifierdeny with remedy or remind
before_replymissing duties and procedure steps, with datafollow-up once
Main risk, seen in our own runs: false denies. The pilot verifier invented a hold code; on the ITSM tuning set, rules on valid tool options and a policy/schema conflict cost 3 tasks. Safeguards: deny only for types with ≤ 2% measured false denies, schema conflicts only remind, repeated-deny cap, firing-rate filter.
Tuning set, 1 trial, partial (2026-11-01): ITSM A 7/10, B 4/10, 8 denies; causes and general fixes in benchmarks/policy_eval/changes.md.
8 · Choosing methods

Measured: code never blocked correct work; model verifiers did, so for 5 types they only remind

  • Check set: 552 cases from reviewed gold builds of the tuning policies (17 types).
  • Rule: deny only with ≤ 2% false denies and ≥ 50% of violations caught; else remind.
  • Kev as a compliance judge caught 0–42% of violations: kept for detection only.
  • Cheaper models won 2 types (gpt-oss-20b), safeguard-20b won filters (0% false denies).
benchmarks/policy_eval/method_comparison.md and method_choice.json (2026-11-01). Gemini 3.8 Flash (reference, never picked) had 6–29% false denies on the same types. The 50% recall floor was added after the first choice picked a judge with recall 0.06 (logged as a change).
9 · Evaluation plan

Tune on 10+10 tasks, freeze, then report only on 10+10 unseen tasks

Unseen10103 trials per arm after the freeze; the only reported result
Cross-reference study25does the agent follow "supersedes", "see …" across records?
  • Arms: A = CUGA alone, B = CUGA + policy layer; same model (Gemini 3.8 Flash), same code otherwise.
  • Primary metrics: AutomationBench AA-style score (any guardrail break = 0); ITSM task pass rate.
  • Also reported: denies, denies the agent went around, reminders, latency, cost, every change made after tuning.
  • Integrity: rules never from graders; task rules fixed before runs; sandbox checks on; run logs scanned for file access.
  • Gold builds (reference for measuring methods): written with the skill by one Claude agent, checked by a second; not reviewed by a person.
Selection rules and seed 20261101: benchmarks/policy_eval/policy_eval_tasks.json (sha256 5e0bf39b…). ITSM unseen tasks share the policy text with tuning (near-identical versions), so ITSM tests new tasks, not a new document.

11 · Answers and decisions

Our answers to the open questions, and what we ask for next

Question (SOTA deck)Our answer
How much of a long policy can become exact rules?Measured per document by the coverage report; ITSM gold: 64 typed rules, 17 checked from text, 15 guidance (96 in all). Handbook-length documents: next, with a section tree
Policy found mid-task: compile or check as text?Both: rule tables compiled at once by code; prose checked as text until compiled; untrusted never enforced
Judgment rules: small open model or large LLM?Small open models by default; picked per type by measurement; large models only as a reference
On a violation: block, or block with an alternative?Deny with a remedy; remind instead when a type's false-deny rate is above 2%
τ2 first, then EnterpriseOps-Gym?Changed: EnterpriseOps-Gym (offline) + AutomationBench (online) first; τ² and HANDBOOK.md next
