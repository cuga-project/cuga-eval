Overview

The short version

One configurable policy system for CUGA, with no benchmark-specific rules. Every result is reported next to whether the tasks were seen during development.

Goal

Follow rules that arrive with the task

Rules hidden in emails and sheets, long SOP documents, step-by-step support flows and rule lists with exceptions. Start with small open models (gpt-oss-120b), not frontier models.

What works

Control for a small agent; a strong checker for a strong one

Full control raised gpt-oss by +18.9 and +8.8 points on two sets that were held out when first run (now labeled seen). The same control hurt Gemini 3.8. For Gemini, a narrow check before each write helped; with gpt-oss as the checker, the same check gave no gain.

What does not

More knowledge, and imprecise feedback

The SOP as a graph of tools gave no gain. Checklists with wrong items made the agent change correct work. Naming a failed check without its value adds only +4 to +6 points. Rules shown without their exceptions caused refusals.

Still open

Held-out proof per model

On 35 new tasks run once (fresh3), polisys raised gpt-oss by +10.4 partial (p = 0.028) and gave Haiku 5.5 no gain, so it stays off for Haiku. Reading every record finds 93% of the rules, but finding is not following: runs that had every rule still passed strict in 25%. Next is one frozen run on a fresh set. See what comes next.

Policies come in four shapes, and each shape needs a different method

Shape 1

Given SOP with procedures

A long document with procedures, templates and exceptions. Example: HANDBOOK.

Shape 2

Rules scattered in data

A "Policy" sheet, an email from the COO that overrides an older rule. Example: AutomationBench.

Shape 3

Step-by-step flow

A troubleshooting manual with paths and branch questions. Example: τ² Telecom.

Shape 4

Rule list with exceptions

"Basic economy cannot be modified", unless the cabin changes first. Example: τ² airline.

System architecture

One policy package, one runtime, attached to CUGA's lifecycle hooks

The architecture as built at the stability gate (2026-11-05, tag policy/stable-v1 on gate commit 9135be1f4). Since 2026-11-05 the policy system is its own package, polisys (cuga-project/polisys); CUGA calls it through the lifecycle hooks of PR #1103. Click any box to see what it does, where the code is, and how far it is built. Dashed boxes were built in the stabilization plan and have not run live. Full text: design spec.

Control levels: the stronger the agent, the less control

0Observe

Trace and audit only.

Measuring, shadow mode
1Advise

Find the rules and SOP parts; show the brief and notes. Only hard rules stop work. The obligation ledger records and sends nothing at this level (it builds no checklist).

Strong agent, rules only in data (Gemini on AutomationBench)
2Check

Level 1, plus procedure tools, narrow questions, the judgment gate and one obligation follow-up.

Strong or mid agent with a package (Gemini + gate on HANDBOOK)
3Control

Level 2, plus a verifier on specific statements, guide, SOP loop, tracker and a second obligation follow-up.

Small models (gpt-oss)
Hard rules deny at levels 1–3; level 0 only records what it would do. High-risk actions (money, external email, delete) get level-3 checks for any model. Each rule can also set its own level. The level switch is built (levels.py), but no profile uses it: the 9 profiles list their components, so the table is a hypothesis until the level by model experiment. Read-before-write is a setting of the online intake, not a level. Adaptive selection is deferred until static levels are measured.

How we test

Eleven rules for a fair result

Most were added after a result turned out to be wrong.

Rule 1

All arms at the same time

From one frozen code snapshot. An arm A run 3 hours earlier gave a false +13.8.

Rule 2

Held-out next to tuning

Tune on one split, run the test split once. Report both numbers.

Rule 3

No task-specific fixes

Every change is a general rule, logged with its reason in changes.md.

Rule 4

No grader data in the system

Rubrics and tests are for scoring only. Graphs are built from the SOP text alone.

Rule 5

Count each task once

Per-task sign test. Counting runs instead of tasks turned p = 0.146 into a false 0.041.

Rule 6

Pool all rounds

Report the pooled result, not the best round: HANDBOOK +14.2 pooled, not +20.3.

Rule 7

Official splits and simulator

The first 20 Telecom tasks gave 18/20; the official test split gave 19/40.

Rule 8

Replay before live

Run a new checker over saved runs first. Replay predicted no gate effect on ITSM for about $0.53.

Rule 9

Two fidelity reports

Test rules against the policy text and against real use. On ITSM the two disagree.

Rule 10

No harm, per model

policy − no policy ≥ −2 × SE on strict and partial, for every model and benchmark, never averaged. A model that fails has the policy system off.

Rule 11

Decide the rule before the run

Write the metric and threshold first, run independent trials with the cache off, and run a fresh set once, frozen, with 3 trials. A set whose failures we traced becomes a tuning set.
